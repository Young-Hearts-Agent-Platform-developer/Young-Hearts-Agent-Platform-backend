## 研究问题

目标：参考 `app/services/user_service.py` 的类型使用方式，提出对 `app/services/knowledge_service.py` 的类型注释优化建议，包含具体修改位置、示例签名与潜在风险/开放问题。

## 发现摘要

  1) 容器/默认值类型不精确或存在隐含 bug（如 schema 中 `tags: List[str] = []`，见 [app/schemas/knowledge.py](app/schemas/knowledge.py#L6-L12)）；
  2) 更新接口复用 Create schema（无 Update schema），使得 `update_knowledge_item` 的类型不准确（見 [app/services/knowledge_service.py](app/services/knowledge_service.py#L20-L30)）；
  3) ingest 路径的签名与返回类型缺少明确注释（`ingest_knowledge` 的实现返回 ORM 实例，見 [app/knowledge/ingest.py](app/knowledge/ingest.py#L12-L35)），而服务层 `ingest_knowledge_item` 未声明返回类型并包含死代码（見 [app/services/knowledge_service.py](app/services/knowledge_service.py#L47-L62)）。

## 开放问题（处理结果）

- `KnowledgeItemUpdate`：已由用户接受，在 `app/schemas/knowledge.py` 中新增该 schema（见推荐步骤）。
- 服务层返回类型策略：用户决定保持现有结构（暂不修改服务层返回 ORM vs schema 的策略）。

## 当前实现分析（关键片段与行号）

 - create_knowledge_item: [app/services/knowledge_service.py](app/services/knowledge_service.py#L9-L19) — 使用 `KnowledgeItemCreate` 与返回 `KnowledgeItem`，注意 `item_in.model_dump(...)`（pydantic v2 方法）与 `KnowledgeItem(**data, ...)` 的字段对齐（schema 默认值与 ORM 字段类型需匹配）。
 - ingest_knowledge_item: [app/services/knowledge_service.py](app/services/knowledge_service.py#L47-L62) — 当前签名使用裸 `list`，未声明返回类型；实际底层 `ingest_knowledge` 在 [app/knowledge/ingest.py](app/knowledge/ingest.py#L12-L35) 中构造并返回 ORM `KnowledgeItem`，因此服务层应声明 `-> KnowledgeItem` 并移除末尾的死代码 `return True`。
 - get_knowledge_item / update_knowledge_item / delete_knowledge_item: 已使用 `Optional[KnowledgeItem]` 和 `bool`（[app/services/knowledge_service.py](app/services/knowledge_service.py#L20-L40)），但 `update_knowledge_item` 目前接受 `KnowledgeItemCreate`（用于创建，不适合部分更新）並调用 `item_in.dict(exclude_unset=True)`，说明预期为“部分更新”语义，应引入 `KnowledgeItemUpdate`（或使用 `Mapping[str, Any]`）以提高类型准确性。
 - create_knowledge_chunk / get_knowledge_chunks_by_item: 已基本正确（[app/services/knowledge_service.py](app/services/knowledge_service.py#L80-L89)），但仍建议为 chunk 更新引入 Update schema（如有需要）。

## 建议的类型注释优化（具体、可复制）

总体建议：
 - 修复 schema 中的可变默认值：将 `tags: List[str] = []`（[app/schemas/knowledge.py](app/schemas/knowledge.py#L6-L12)）替换为 `tags: List[str] = Field(default_factory=list)`，避免共享可变默认导致的运行时 bug。
 - 为部分更新创建 `KnowledgeItemUpdate`（所有字段 Optional），并在 `update_knowledge_item` 中使用该类型；若暂不添加 schema，可使用 `Mapping[str, Any]` 作为过渡。
 - 将 `ingest_knowledge_item` 的签名改为 `tags: Optional[List[str]] = None` 并声明返回类型为 `KnowledgeItem`（或 `KnowledgeItemRead`，若希望服务层返回 schema），同时移除死代码。
 - 明确服务层返回 ORM vs schema 的团队约定；建议服务层返回 schema（如 `KnowledgeItemRead`），这一做法更利于边界清晰与序列化。

    ## 风险与注意事项

     - `app/schemas/knowledge.py` 使用 pydantic（文件顶部 `BaseModel`），且服务层在创建时调用 `item_in.model_dump(...)`（pydantic v2 方法），所以假定项目使用 pydantic v2；若不是，`model_dump` 调用需调整。
     - schema 中的可变默认（`tags: List[str] = []`）会在运行时造成不同实例间共享同一列表，建议尽快替换为 `Field(default_factory=list)`（已在建议中列出）。
     - 修改签名与新增 `KnowledgeItemUpdate` 后，请运行单元测试（`pytest`）并在 CI 中运行静态检查（`mypy` / `pyright`），以捕获跨模块不匹配。
