## 发现摘要

当前代码库中 `app/services/knowledge/` 和 `app/services/rag/` 的目录结构与 `docs/“心青年”智能体平台-项目结构.md` 中定义的设计规范存在偏差。当前实现将 RAG 管道、检索器和向量库放在了 `knowledge/` 目录下，而设计文档要求将所有 RAG 核心组件（如 `chains/`, `embeddings/`, `splitters/`, `vectorstore/`）统一收敛到 `app/services/rag/` 模块中。同时，知识库的 CRUD 业务逻辑应独立为 `app/services/knowledge_service.py`，耗时的文档解析与向量化入库操作应交由 `app/tasks/knowledge_tasks.py` 异步处理。

## 当前实现分析

目前代码库中的结构如下：
- `app/services/knowledge/` 包含了 `ingest.py`（文档录入）、`rag_pipeline.py`（RAG 管道）、`retriever.py`（检索器）以及 `vectorstore/` 目录。这些文件目前多为占位符（Stub）。
- `app/services/rag/` 包含了 `service.py`（调用大模型生成回复）和 `prompts/` 目录。

这种结构将 RAG 的核心组件（检索、向量库）与知识库的业务逻辑（录入）混杂在了一起，且与项目结构设计文档不符。根据设计文档，`app/services/rag/` 应该是一个独立的、与普通业务逻辑解耦的 RAG 引擎核心模块，而知识库的管理（如元数据的 CRUD）应该属于普通的业务逻辑层。

### 核心流程

根据功能文档和技术栈设计，知识库与 RAG 的核心流程分为两条线：

**1. 数据入库流（双写机制）**
```text
用户上传文档 (API) 
  -> knowledge_service.py (保存元数据到 MySQL，状态为"待处理")
  -> 触发 Celery 异步任务 (knowledge_tasks.py)
  -> rag/splitters/ (文档切片)
  -> rag/embeddings/ (调用 Embedding API)
  -> rag/vectorstore/ (存入 ChromaDB)
  -> 更新 MySQL 状态为"已发布"
```

**2. 检索问答流 (RAG)**
```text
用户提问 (API)
  -> rag/service.py (RAG 服务入口)
  -> rag/chains/ (构建检索问答链)
  -> rag/vectorstore/ (在 ChromaDB 检索 Top-K 相关片段)
  -> 组装 Prompt (结合检索结果与 System Prompt)
  -> 调用 LLM 生成回答并返回
```

## 架构洞察

- **职责分离**：`app/services/rag/` 应纯粹作为底层 AI 引擎，封装 LangChain、ChromaDB 和大模型交互；而 `app/services/knowledge_service.py` 作为业务服务，负责处理 HTTP 请求带来的业务逻辑（如权限校验、MySQL 记录创建），两者通过函数调用或异步任务解耦。
- **异步处理**：文档的解析、切片和向量化是耗时操作，必须通过 Celery 任务（`app/tasks/knowledge_tasks.py`）异步执行，以保证 API 的响应速度。
- **双写架构**：知识库数据需要同时存在于 MySQL（用于后台管理、列表展示、权限控制）和 ChromaDB（用于语义检索）。

## 潜在风险和边缘情况

- **数据一致性风险**：MySQL 中的知识库元数据状态与 ChromaDB 中的向量数据可能出现不一致（例如向量化失败但 MySQL 状态已更新）。需要在异步任务中增加完善的错误处理和状态回滚机制。
- **目录迁移风险**：重构现有 `knowledge/` 目录可能会影响已经依赖这些占位符的测试用例或其他模块，需要同步更新相关的 import 路径。

## 开放问题

- 是否需要立即引入 Celery 进行异步任务处理，还是在 MVP 阶段先使用 FastAPI 的 `BackgroundTasks` 作为过渡？
- 向量数据库 ChromaDB 的具体部署方式（内存模式还是独立容器）是否已在本地开发环境中就绪？

## 建议的重构操作

1. **删除/重命名目录**：将 `app/services/knowledge/` 目录下的 RAG 相关组件（`vectorstore/`, `retriever.py`, `rag_pipeline.py`）迁移至 `app/services/rag/` 目录下。
2. **创建业务服务**：新建 `app/services/knowledge_service.py`，用于处理知识库的 CRUD 业务逻辑。
3. **完善 RAG 结构**：在 `app/services/rag/` 下建立 `chains/`, `embeddings/`, `splitters/` 等子目录，以符合 LangChain 的最佳实践。
4. **创建异步任务**：新建 `app/tasks/knowledge_tasks.py`，将 `ingest.py` 中的逻辑迁移至此，实现文档的异步处理流水线。
