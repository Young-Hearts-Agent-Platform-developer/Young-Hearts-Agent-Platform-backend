## 研究问题

如何全面测试知识库、RAG 功能（要求连接到真实的嵌入模型和数据库）？

## 发现摘要

1. 当前测试（如 `test_rag_chain.py`）主要依赖 Mock，无法验证真实 Embedding 模型和向量数据库的连通性与检索效果。
2. 知识库处理流程（`process_knowledge_document`）是异步的，测试时需要同步调用以确保数据入库。
3. ChromaDB 集合名称（`"knowledge_base"`）在代码中硬编码，测试时容易污染开发/生产数据，需改为配置项。
4. 全面测试需要构建端到端（E2E）集成测试，涵盖：知识创建 -> 同步切片向量化 -> 真实大模型对话 -> 检索结果验证。

## 当前实现分析

1. **知识入库**：知识库上传后，通过 Celery 异步触发 `process_knowledge_document` 任务。该任务读取文档内容，使用 `CustomSplitter` 进行切片，调用 `DoubaoEmbeddings` 生成向量，并存入 ChromaDB（集合名硬编码为 `"knowledge_base"`）。
2. **知识检索与生成**：用户提问时，`/api/consult/chat` 接口调用 `async_chat_with_rag`，后者通过 `retrieve_context` 从 ChromaDB 检索相关片段，组装 Prompt 后调用大模型生成回复。

### 核心流程 (端到端测试方案)

```text
[环境准备] -> 加载 .env.test (真实 API Key) -> 初始化独立测试 DB 和 Chroma 集合
   |
[数据准备] -> 创建测试用户 -> 获取 Token
   |
[知识注入] -> POST /api/knowledge/ (创建知识条目)
   |
[同步处理] -> 直接调用 process_knowledge_document(doc_id) (绕过 Celery 异步)
   |
[RAG 验证] -> POST /api/consult/sessions (创建会话)
   |       -> POST /api/consult/chat (发送包含特定罕见词的 Query)
   |       -> 断言 SSE 响应包含预期知识点及正确的 sources
   |
[环境清理] -> 清空测试 DB 和 Chroma 集合
```

**2. 集成测试用例示例 (`tests/integration/test_rag_integration.py`)**

```python
import pytest
from fastapi.testclient import TestClient
from app.main import app
from app.tasks.knowledge_tasks import process_knowledge_document
from app.core.config import settings
from app.services.rag.vectorstore.chroma import get_chroma_collection

# 标记为集成测试，可在日常运行中跳过
@pytest.mark.integration
def test_end_to_end_rag_flow(client: TestClient, admin_token: dict, db):
    # 1. 确保使用测试专用的 Chroma 集合
    assert settings.CHROMA_COLLECTION_NAME == "test_knowledge_base"
    
    # 2. 创建知识条目 (包含罕见词汇以便于检索验证)
    rare_keyword = "测试专用罕见词汇X99"
    knowledge_data = {
        "title": "集成测试文档",
        "content": f"这是一个用于集成测试的文档。核心知识点是：{rare_keyword}代表一种特殊的测试状态。",
        "category": "test",
        "risk_level": "low",
        "status": "published"
    }
    
    resp = client.post("/api/knowledge/", json=knowledge_data, headers=admin_token)
    assert resp.status_code == 200
    doc_id = resp.json()["id"]
    
    # 3. 同步执行向量化任务 (绕过 Celery)
    process_knowledge_document(doc_id)
    
    # 4. 创建咨询会话
    resp = client.post("/api/consult/sessions", json={"topic": "测试会话"}, headers=admin_token)
    assert resp.status_code == 200
    session_id = resp.json()["id"]
    
    # 5. 发起 RAG 对话请求
    chat_req = {
        "query": f"请问{rare_keyword}代表什么？",
        "role": "default",
        "session_id": session_id
    }
    
    # 由于是流式接口，需要特殊处理响应
    with client.stream("POST", "/api/consult/chat", json=chat_req, headers=admin_token) as response:
        assert response.status_code == 200
        full_response = ""
        for line in response.iter_lines():
            if line and line.startswith("data: "):
                data_str = line[6:]
                if data_str != "[DONE]":
                    import json
                    data = json.loads(data_str)
                    if data.get("event") == "message":
                        full_response += data.get("data", "")
        
        # 6. 断言大模型回答中包含了我们注入的知识
        assert "特殊的测试状态" in full_response
        
    # 7. 清理测试数据
    vectorstore = get_chroma_collection(settings.CHROMA_COLLECTION_NAME)
    vectorstore.delete_collection()
```

## 架构洞察

- **配置隔离的重要性**：当前系统在向量数据库集合名称上存在硬编码，这在引入真实数据库的集成测试时会成为痛点。通过环境变量注入集合名称是实现测试隔离的关键。
- **异步任务的同步化测试**：在微服务或包含 Celery 的架构中，端到端测试通常需要将异步任务同步化（如直接调用 task 函数），或者引入轮询机制等待异步任务完成。直接调用函数是目前最简单可靠的方式。

## 潜在风险和边缘情况

- **费用与限流**：真实调用大模型和 Embedding API 会产生费用，且可能触发并发限流（Rate Limit），导致测试偶发失败（Flaky tests）。
- **网络延迟**：依赖外部 API 会增加测试执行时间，建议将此类测试标记为 `@pytest.mark.integration`，在日常开发中跳过，仅在 CI/CD 特定阶段运行。
- **并发冲突**：如果多个集成测试同时运行并共享同一个测试 Chroma 集合，可能会导致数据串扰。建议每个测试用例生成一个带有 UUID 的独立集合名，测试结束后销毁。

## 开放问题

- **评估指标**：目前的测试仅验证了“流程通畅”和“能查到特定词汇”。是否需要引入 Ragas 或 TruLens 等专业的 RAG 评估框架，以量化测试检索的准确率（Precision/Recall）和生成的幻觉率？
- **CI/CD 策略**：在 GitHub Actions 等 CI 环境中，如何安全地管理和注入真实的 API Key？是否考虑在 CI 中使用轻量级的本地模型（如 Ollama）替代真实的线上大模型以节省成本？
