## 研究问题

1. 添加获取个人知识贡献历史的 API 接口供前端调用。
2. 判断 `POST /api/knowledge/upload` 与 `POST /api/knowledge/items` 两个接口的功能是否重叠。
3. 目前是否实现修改特定 item？
4. 为 `GET /api/knowledge/items` 返回的结果进行隐私处理，匿去敏感信息（为 `***`）。

## 发现摘要

1. **个人贡献历史接口**：当前系统缺乏获取个人知识贡献历史的专用接口。建议新增 `GET /api/knowledge/my-items` 接口，并在 `KnowledgeService.list_items` 中增加 `author_id` 过滤参数。根据确认，该接口无需支持按状态过滤。
2. **接口重叠分析**：`POST /api/knowledge/upload` 与 `POST /api/knowledge/items` 存在功能重叠。根据确认，将删除 `POST /api/knowledge/items` 接口，统一使用 `POST /api/knowledge/upload` 接口进行知识条目的创建（包括纯文本和文件）。
3. **修改特定条目**：目前已实现修改特定条目的接口 `PUT /api/knowledge/items/{item_id}`，支持作者本人或管理员/专家进行修改。
4. **隐私处理需求**：`GET /api/knowledge/items` 作为公开接口，当前直接返回了完整的数据库字段（如 `file_path`, `review_comments`, `reviewed_by` 等）。需要对这些可能暴露内部系统结构或审核细节的敏感信息进行脱敏处理（替换为 `***`）。

## 当前实现分析

### 1. 个人知识贡献历史接口

目前，获取知识条目列表的接口为 `GET /api/knowledge/items`，其实现如下：

```python
# app/api/v1/routes/knowledge.py L43-L51
@router.get("/items", response_model=KnowledgeItemListResponse)
async def list_items(
    status: Optional[str] = Query("published", description="Filter by status"),
    skip: int = Query(0, ge=0),
    limit: int = Query(20, ge=1, le=100),
    service: KnowledgeService = Depends(get_knowledge_service)
):
    total, items = service.list_items(status=status, skip=skip, limit=limit)
    return {"total": total, "items": items}
```

该接口未要求用户登录（无 `current_user` 依赖），且底层的 `KnowledgeService.list_items` 方法仅支持按 `status` 过滤，不支持按 `author_id` 过滤。因此，前端无法通过现有接口获取当前用户的贡献历史。

### 2. 接口重叠分析

#### `POST /api/knowledge/items`
该接口接收 JSON 格式的 `KnowledgeItemCreate` 数据，直接在数据库中创建 `KnowledgeItem` 记录。如果状态为 `published`，则触发 `vectorize_knowledge_document` 异步任务；否则触发 `extract_knowledge_text` 任务。该接口不处理文件上传，仅处理文本内容和元数据。

#### `POST /api/knowledge/upload`
该接口接收 `multipart/form-data` 格式的数据，支持文件上传（`file` 字段）和纯文本上传（`text_content` 字段）。
- 当提供 `text_content` 时，接口会将其保存为本地的 `.txt` 文件，并将文件路径和文本内容一并存入数据库。
- 随后，它同样调用 `service.create_item` 创建记录并触发相同的异步任务。

#### 核心流程对比

- **纯文本创建流程 (items 接口)**：
  前端发送 JSON -> `create_item` -> 存入 DB (`content` 有值，`file_path` 为空) -> 触发 Celery 任务 -> 任务读取 DB 中的 `content` 进行向量化。
- **纯文本创建流程 (upload 接口)**：
  前端发送 Form Data -> 保存为本地 `.txt` 文件 -> `create_item` -> 存入 DB (`content` 有值，`file_path` 有值) -> 触发 Celery 任务 -> 任务优先读取 DB 中的 `content` 进行向量化。

### 3. 修改特定条目接口

目前系统已实现 `PUT /api/knowledge/items/{item_id}` 接口用于修改特定知识条目。

```python
# app/api/v1/routes/knowledge.py L63-L72
@router.put("/items/{item_id}", response_model=KnowledgeItemResponse)
async def update_item(
    item_id: int,
    req: KnowledgeItemUpdate,
    current_user: User = Depends(get_current_user),
    service: KnowledgeService = Depends(get_knowledge_service)
):
    user_id = int(getattr(current_user, 'id', 0))
    roles = get_user_roles(current_user)
    return service.update_item(item_id=item_id, user_id=user_id, data=req, user_roles=roles)
```

在 `KnowledgeService.update_item` 中，已包含权限校验逻辑：仅允许条目的原作者，或拥有 `admin`/`expert` 角色的用户进行修改。如果状态被修改为 `published`，还会重新触发向量化异步任务。

### 4. 公开列表接口的隐私处理

`GET /api/knowledge/items` 接口当前返回 `KnowledgeItemListResponse`，其中包含的 `KnowledgeItemResponse` 暴露了以下潜在敏感字段：
- `file_path`: 服务器内部文件路径。
- `review_comments`: 专家的内部审核意见。
- `reviewed_by`: 审核专家的 ID。

由于该接口是公开的（无需鉴权），直接暴露这些信息存在隐私和安全风险。需要修改该接口的返回逻辑或响应模型，将这些敏感字段的值替换为 `***`。

## 架构洞察

- **统一的创建入口**：通过删除 `POST /api/knowledge/items` 并统一到 `POST /api/knowledge/upload`，简化了 API 设计，前端只需对接一个接口即可完成纯文本和文件的上传，降低了对接成本。
- **公开数据的脱敏**：公开接口与内部管理接口应使用不同的响应模型（Schema），以确保内部敏感数据（如文件路径、审核记录）不会意外泄露给未授权用户。

## 潜在风险和边缘情况

- **数据不一致**：如果使用 `upload` 接口提交纯文本，本地文件系统会产生大量 `.txt` 文件。如果这些文件被意外删除，虽然数据库中仍有 `content`，但 `file_path` 指向的文件已丢失，可能在某些依赖文件路径的边缘逻辑中引发错误。
- **前端调用困惑**：前端开发者在提交纯文本知识时，可能不清楚应该调用 `items` 接口还是 `upload` 接口，增加了对接成本。

## 开放问题

1. **隐私处理的具体字段**：对于 `GET /api/knowledge/items`，除了 `file_path`, `review_comments`, `reviewed_by` 之外，是否还有其他字段（如 `author_id`）需要脱敏为 `***`？
    回答：暂无
2. **脱敏方式**：是倾向于在现有 `KnowledgeItemResponse` 模型中将敏感字段的值修改为 `***`，还是倾向于定义一个新的 `KnowledgeItemPublicResponse` 模型直接不返回这些字段？（通常推荐后者以减少带宽，但根据需求描述“匿去敏感信息（为 ***）”，可能需要前者）。
    回答：前者。
