## 研究问题

知识库及RAG 功能实现的完整性

## 发现摘要

当前知识库与 RAG 模块已具备基础的端到端能力，包括知识条目的 CRUD、基于 Celery 的异步文档处理（切片、向量化）、基于风险等级的差异化切片策略（高/低风险直接切片，中风险使用父子文档检索），以及在咨询会话中集成 RAG 检索。但仍存在一些关键缺口：文件上传接口未实现、多模态解析缺失、关系型数据库中的切片模型（`KnowledgeChunk`）未被使用，以及检索来源未在会话中持久化。

## 当前实现分析

### 核心流程

1. **知识录入与发布**：
   - 用户通过 `/items` 接口创建知识条目。
   - 当条目状态变更为 `published` 时，`KnowledgeService` 会触发 Celery 异步任务 `process_knowledge_document`。
2. **异步文档处理**：
   - 任务读取文档内容，目前仅支持纯文本解析（多模态解析为 TODO）。
   - 根据文档的 `risk_level` 采用不同的切片策略：
     - **中风险**：使用 `ParentDocumentRetriever`，将父块存入本地文件系统（`LocalFileStore`），子块存入 ChromaDB。
     - **高/低风险**：直接使用 `CustomSplitter` 切片，并将结果存入 ChromaDB。
3. **RAG 检索与生成**：
   - 用户在咨询会话中发送消息，`/chat` 接口调用 `async_chat_with_rag`。
   - `retrieve_context` 首先在 ChromaDB 中进行相似度检索，获取相关子块。
   - 如果子块属于中风险文档（有父文档 ID），则从 `LocalFileStore` 中提取父文档作为上下文；否则直接使用子块。
   - 组装上下文后，结合角色 Prompt 和用户 Query，调用大模型生成流式回复。

## 架构洞察

- **灵活的切片策略**：系统根据文档的风险等级（`risk_level`）动态选择切片策略，中风险文档采用父子文档检索（Parent-Child Retrieval）以保留更多上下文，高/低风险文档则采用直接切片，这种设计在检索精度和上下文完整性之间取得了较好的平衡。
- **检索回退机制**：`retrieve_context` 在尝试获取父文档失败时，会自动回退使用检索到的子块，这使得系统能够兼容不同风险等级文档的混合检索。

## 潜在风险和边缘情况

- **距离与相似度转换风险**：在 `retrieve_context` 中，当 ChromaDB 不支持 `relevance_scores` 时，代码使用 `max(0.0, 1.0 - score / 2.0)` 将 L2 距离转换为相似度得分。这是一个简单的线性转换，可能无法准确反映实际的语义相似度，导致低于阈值的无关文档被召回，或相关文档被过滤。
- **数据一致性风险**：切片数据仅存储在 ChromaDB 和本地文件系统中，未同步到关系型数据库的 `KnowledgeChunk` 表。如果向量数据库或本地文件系统损坏，将难以从关系型数据库重建切片关系。

## 开放问题

1. **文件上传未实现**：`app/api/v1/routes/knowledge.py` 中的 `/upload` 接口目前仅为占位符，未实现文件的实际接收、保存和触发解析流程。
2. **多模态解析缺失**：`app/tasks/knowledge_tasks.py` 中的 `parse_document_content` 函数对于 PDF、图片、音视频等格式仅预留了接口，实际仍作为纯文本处理。
3. **`KnowledgeChunk` 模型闲置**：`app/models/knowledge.py` 中定义了 `KnowledgeChunk` 模型，但在切片入库时并未将其持久化到 MySQL 中，导致后台无法管理和查看具体的切片结果。
4. **检索来源未持久化**：在 `app/api/v1/routes/consult.py` 中，调用 `save_ai_message_and_generate_topic` 时，`sources` 参数被硬编码为 `None`，导致用户无法在历史会话中追溯 AI 回复的知识来源。
