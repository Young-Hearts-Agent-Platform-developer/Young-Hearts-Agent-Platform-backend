## 发现摘要

知识库的 CRUD 功能涉及 `KnowledgeItem` 模型的创建、读取、更新、软删除以及审核流程。测试用例设计需要覆盖 Service 层的核心业务逻辑（如权限校验、状态流转、软删除过滤）以及 API 层的路由鉴权、参数校验和 HTTP 状态码返回。当前 Service 层已有部分基础测试，但需要进一步完善边界条件和异常场景的覆盖；API 层则需要重点测试不同角色（volunteer, expert, admin, family）的访问权限。

## 当前实现分析

知识库的 CRUD 操作主要由 `KnowledgeService` 提供，并通过 `app/api/v1/routes/knowledge.py` 暴露为 RESTful API。

### 核心流程

1. **创建 (Create)**: 
   - API: `POST /items`，要求用户角色为 `volunteer`, `expert` 或 `admin`。
   - Service: `create_item`，将 `author_id` 绑定为当前用户，默认状态为 `draft` 或传入的 `pending_review`。
2. **读取 (Read)**:
   - API: `GET /items` (列表) 和 `GET /items/{item_id}` (详情)，目前为公开接口（无 `current_user` 依赖）。
   - Service: `list_items` 和 `get_item`，均会过滤掉 `is_deleted == True` 的软删除记录。`list_items` 支持按 `status` 过滤和分页。
3. **更新 (Update)**:
   - API: `PUT /items/{item_id}`，要求登录用户。
   - Service: `update_item`，校验权限：仅允许作者本人或拥有 `admin`/`expert` 角色的用户修改。
4. **删除 (Delete)**:
   - API: `DELETE /items/{item_id}`，要求登录用户。
   - Service: `delete_item`，校验权限同更新操作，执行软删除（设置 `is_deleted = True`）。
5. **审核 (Audit)**:
   - API: `GET /audit-list` 和 `POST /{item_id}/audit`，要求用户角色为 `expert` 或 `admin`。
   - Service: `audit_item`，校验当前状态必须为 `pending_review`，更新状态为 `published` 或 `rejected`，并记录审核人信息。

## 测试用例设计方案

### 1. Service 层测试用例 (`tests/knowledge/test_knowledge_service.py`)

Service 层测试应直接调用 `KnowledgeService` 的方法，使用内存 SQLite 数据库（`db_session` fixture），重点验证业务逻辑和数据持久化。

| 测试场景 | 目标方法 | 预期结果 |
|---|---|---|
| **创建知识条目** | `create_item` | 成功返回包含 ID 的 `KnowledgeItem` 对象，数据库中存在该记录。 |
| **获取存在的条目** | `get_item` | 成功返回对应的 `KnowledgeItem` 对象。 |
| **获取不存在的条目** | `get_item` | 抛出 `HTTPException(status_code=404)`。 |

| **作者更新条目** | `update_item` | 成功更新指定字段，返回更新后的对象。 |
| **管理员/专家更新他人条目** | `update_item` | 成功更新指定字段。 |
| **普通用户更新他人条目** | `update_item` | 抛出 `HTTPException(status_code=403)`。 |
| **作者删除条目** | `delete_item` | 成功执行软删除，再次 `get_item` 抛出 404。 |

## 架构洞察

- **软删除机制**：当前系统采用软删除（`is_deleted` 字段），这在知识库场景下是合理的，可以保留历史数据和关联关系。测试时必须确保所有查询接口（如 `get_item`, `list_items`）都正确过滤了软删除的数据。
- **权限控制分散**：API 层进行了初步的角色拦截（如 `POST /items` 限制 `volunteer` 等），而 Service 层进行了更细粒度的资源所有权校验（如 `update_item` 校验 `author_id`）。测试用例需要分别覆盖这两层的校验逻辑。
- **公开读取接口**：目前的 `GET /items` 和 `GET /items/{id}` 接口没有强制要求登录（未注入 `current_user`）。如果这是设计预期（允许游客浏览已发布的知识），则测试用例应包含未登录状态下的成功读取测试。

## 潜在风险和边缘情况

- **并发更新/审核**：如果两个专家同时审核同一个条目，后一个请求可能会覆盖前一个请求的结果，或者在状态已经变为 `published` 后再次审核导致 400 错误。
- **软删除后的唯一性约束**：虽然当前模型没有对 `title` 做唯一性约束，但如果未来添加，软删除的记录可能会导致同名新记录创建失败。
- **分页越界**：当 `skip` 远大于实际数据总量时，应返回空列表而不是报错。
