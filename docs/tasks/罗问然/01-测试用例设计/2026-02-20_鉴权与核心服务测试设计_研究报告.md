## 研究问题

根据目前项目的实现方式（尤其注意登录方式），设计测试用例，分别用于测试 `auth`、`user_service`、`consultation_service` 三个服务。需格外注意接口的权限验证方式，并尽量复用登录状态。

## 发现摘要

1.  **鉴权机制**：项目主要采用 **Session ID** 机制。登录成功后，服务器生成 `session_id` 存入数据库，并通过 `Set-Cookie` (Web端) 或响应体 (App/API端) 返回。后续请求需携带此 Cookie 或 Header。同时也保留了 OAuth2PasswordBearer 的痕迹，但在 `login` 路由中主要由 Session 主导。
2.  **权限控制**：
    *   **路由层**：使用自定义装饰器 `@require_roles` 配合 `Depends(get_current_user)` 进行角色拦截。
    *   **服务层**：部分服务（如 `ConsultationService`）在方法内部通过 `user_id` 对比和 `is_admin` 检查进行行级权限控制（Row-Level Security）。
3.  **测试策略**：测试需模拟完整的“登录 -> 获取 Session -> 携带 Session 访问受保接口”流程。

## 当前实现分析与测试设计

### 1. 通用测试夹具 (Fixtures) 设计

为了“尽量复用登录状态”，应设计 Pytest Fixtures 来管理 Session。

**核心流程：**
1.  **Client Fixture**: 创建 `TestClient`。
2.  **User Fixture**: 在数据库创建一个测试用户（如 "test_user"）。
3.  **Auth Headers Fixture**:
    *   调用 `/api/v1/auth/login` 接口登录 "test_user"。
    *   从响应 Cookie 或 Body 中提取 `session_id`。
    *   构造包含 Cookie 的 Header：`{"Cookie": f"session_id={session_id}"}`。
4.  **Admin Headers Fixture**: 类似普通用户，但创建一个具有 "admin" 角色的用户并登录。

### 2. Auth 服务测试用例

主要关注 `app/api/v1/routes/auth.py` 和 `app/services/auth.py`。

| 测试场景 | 步骤概要 | 预期结果 |
|---|---|---|
| **正常登录** | POST /auth/login (正确账号密码) | 200 OK, 返回用户信息, Set-Cookie 包含 session_id |
| **错误密码登录** | POST /auth/login (错误密码) | 401 Unauthorized |
| **不存在用户登录** | POST /auth/login (不存在账号) | 401 Unauthorized |
| **获取当前用户 (Me)** | GET /auth/me (带有效 Cookie) | 200 OK, 返回当前用户信息 |
| **未登录访问 Me** | GET /auth/me (无 Cookie) | 401 Unauthorized |
| **注销** | POST /auth/logout (带 Cookie) -> GET /auth/me | Logout 200 OK -> Me 401 Unauthorized |
| **注册新用户** | POST /auth/register (新用户名) | 200 OK, 数据库存在该用户 |
| **注册冲突** | POST /auth/register (已存在用户名) | 400/409 Error (视具体实现而定) |
| **非法角色注册** | POST /auth/register (尝试注册 "admin" 角色) | 403 Forbidden (基于代码 L70) |

### 3. User Service 测试用例

主要关注 `app/services/user_service.py` 和 `app/api/v1/routes/auth.py` (用户信息修改部分)。

**注意**：User Service 的很多逻辑直接在 Auth 路由中暴露，测试路由即可覆盖 Service。

| 测试场景 | 步骤概要 | 预期结果 |
|---|---|---|
| **修改个人信息** | PUT /auth/me (更新 nickname) | 200 OK, 再次 GET /auth/me 确认更新 |
| **修改受限字段** | PUT /auth/me (尝试更新 password/roles) | Password 应被忽略或报错，Roles 不可由普通用户更新 |
| **修改他人信息 (越权)** | 尝试构造请求修改 userID != current_user 的数据 | 接口仅暴露 `/me`，理论上无法直接修改他人，需测试 Admin 接口（若有） |
| **Service层: CRUD** | 直接调用 `user_service.create_user` 等函数 | 验证数据库变更 |

### 4. Consultation Service 测试用例

主要关注 `app/api/v1/routes/consult.py` 和 `app/services/consultation_service.py`。

**关键点**：`ConsultationService` 在 `list_sessions_recent` 和 `get_session_detail` 中有显式的权限判断逻辑。

| 测试场景 | 步骤概要 | 预期结果 |
|---|---|---|
| **创建会话** | POST /consult/sessions (带 Auth) | 200 OK, 返回 session_id, user_id 为当前用户 |
| **未登录创建** | POST /consult/sessions (无 Auth) | 401 Unauthorized |
| **获取会话列表** | Create Session A -> GET /consult/sessions | 200 OK, 列表中包含 Session A |
| **数据隔离 (普通用户)** | User A 创建 Session A -> User B 登录 -> GET /consult/sessions | User B 列表 **不包含** Session A |
| **获取会话详情 (本人)** | User A GET /consult/sessions/{SessionA_ID} | 200 OK, 返回详情 |
| **获取会话详情 (越权)** | User B GET /consult/sessions/{SessionA_ID} | 403 Forbidden (基于 `consultation_service.py` L39) or 404 |
| **管理员越权访问** | Admin 登录 -> GET /consult/sessions/{UserA_SessionID} | 200 OK (管理员通过 `is_admin` 检查) |
| **删除会话** | DELETE /consult/sessions/{SessionA_ID} | 200 OK, 再次查询不存在 |
| **删除他人会话** | User B DELETE /consult/sessions/{UserA_SessionID} | 403 Forbidden |

## 风险与建议

1.  **Session 过期测试**：目前的测试设计主要覆盖为了功能性，建议补充测试 Session 过期后的行为（模拟时间流逝或篡改 DB 中的 `expired_at`）。
2.  **CSRF 风险**：当前代码仅通过 Cookie 验证，若未启用 strict SamSite 或 CSRF Token，可能存在风险。测试中可模拟跨域请求行为。
3.  **权限提升风险**：`register` 接口显式禁止了 `admin` 和 `maintainer`，但需测试大小写变种（如 "Admin"）是否绕过检查（当前代码做了 `any(role in ["admin"] ...)` 检查，若是字符串匹配需确认是否严格）。

## 开放问题

1.  **流式响应测试**：`/consult/chat` 接口返回 SSE (Server-Sent Events)，测试客户端需要支持流式读取 (`stream=True`) 才能完整验证。
2.  **Web vs App 鉴权区分**：代码中根据 User-Agent 区分 Cookie 和 Body 返回。测试时需在该处覆盖两种 User-Agent 场景。
