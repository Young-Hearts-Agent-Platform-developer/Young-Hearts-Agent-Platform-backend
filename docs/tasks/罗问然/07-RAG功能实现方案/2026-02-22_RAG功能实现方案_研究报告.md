## 研究问题

根据附件和 `docs` 中的相关文档，研究如何实现 RAG 功能？

## 发现摘要

RAG 功能的实现分为“数据入库流”和“检索问答流”两条主线。数据入库流需通过 Celery 异步任务处理文档切片、向量化并存入 ChromaDB；检索问答流需通过 LangChain 封装检索和 LLM 调用，并包含相似度阈值兜底机制。当前代码库中 `app/services/rag/rag_service.py` 仅实现了基础的 LLM 调用，尚未实现完整的 RAG 逻辑，且 `app/tasks/knowledge_tasks.py` 仍为空。
根据最新澄清，切片策略将严格遵循《孤独症专业资料知识库RAG切片策略选型指南》，采用基于风险分级的定制化切片（如高风险文档的严格结构切片、中风险的混合分层切片），并辅以多维度元信息标注。相似度阈值暂定为 0.6，ChromaDB 将采用 Docker 单机部署（`http://localhost:8000`）。

## 当前实现分析

目前代码库中 `app/services/rag/rag_service.py` 仅实现了 `async_chat_with_rag` 和 `generate_topic` 函数，这些函数直接调用了 `ChatOpenAI` 生成回复，并没有包含从向量数据库（ChromaDB）检索相关文档片段的逻辑。同时，用于处理文档入库的异步任务文件 `app/tasks/knowledge_tasks.py` 尚未实现。

### 核心流程

根据技术栈设计文档，RAG 的核心流程如下：

**1. 数据入库流（异步处理）**
```text
用户上传文档 (API) 
  -> knowledge_service.py (保存元数据到 MySQL，状态为"待处理")
  -> 触发 Celery 异步任务 (knowledge_tasks.py)
  -> rag/splitters/ (使用 LangChain Text Splitter 进行文档切片)
  -> rag/embeddings/ (调用 Embedding API，如 BGE-M3 或 OpenAI Embedding)
  -> rag/vectorstore/ (存入 ChromaDB，Metadata 包含 source_id, page)
  -> 更新 MySQL 状态为"已发布"
```

**2. 检索问答流 (RAG)**
```text
用户提问 (API)
  -> rag/rag_service.py (RAG 服务入口)
  -> rag/chains/ (构建检索问答链)
  -> rag/vectorstore/ (在 ChromaDB 检索 Top-K 相关片段)
  -> 相似度判断 (若低于阈值如 0.6，直接返回“暂无相关信息，建议转人工”)
  -> 组装 Prompt (结合检索结果与 System Prompt)
  -> 调用 LLM 生成回答并返回 (需附带参考的知识库文档名称或链接)
```

## 架构洞察

- **定制化切片策略**：针对孤独症专业资料的特殊性，绝对不能使用通用的一刀切方案。必须先对资料进行分类与风险分级（高/中/低风险）。高风险文档（如诊断标准）采用严格结构切片（100-1024 token，20%重叠）；中风险文档采用混合分层切片（父块 512-2048 token，子块 128-512 token，10%-15%重叠）；低风险文档采用语义切片（64-512 token，5%-10%重叠）。
- **多维度元信息标注与父子块召回**：切片时必须补充标准化元信息（如风险等级、适用年龄、核心分类）。对于中风险文档，采用“子块召回+父块补全”的机制（在 LangChain 中使用 `ParentDocumentRetriever` 实现），既保证召回精准度，又提供完整上下文，避免断章取义。
- **Embedding 模型选型**：开发阶段暂定使用 `Doubao-embedding-large` 作为 API 模型进行向量化。
- **兜底机制**：为了防止大模型产生幻觉，必须在检索阶段设置相似度阈值（暂定为 0.6）。如果检索到的片段相似度过低，应跳过 LLM 生成阶段，直接返回预设的转人工提示。
- **可溯源性**：生成的回答必须附带参考来源。这要求在存入 ChromaDB 时，必须在 Metadata 中详细记录文档的来源信息（如 `source_id`, `page`, `title`），并在组装 Prompt 时要求 LLM 引用这些信息。
- **异步解耦**：文档的解析、切片和向量化是耗时操作，必须通过 Celery 任务异步执行，以保证 API 的响应速度。
- **向量库部署**：ChromaDB 采用 Docker 单机部署，通过 `.env` 配置连接地址（如 `http://localhost:8000`），便于本地开发与生产环境的统一。

## 潜在风险和边缘情况

- **多格式数据源与清洗挑战**：知识库可能包含 PDF、图片等非结构化或半结构化数据源。虽然本阶段不作为核心任务，但未来必须引入 OCR 和版面分析工具进行数据清洗与结构化提取，否则会严重影响切片质量和 RAG 准确性。
- **RAG 准确性风险**：切片策略（如 Chunk Size, Chunk Overlap）和 Prompt Engineering 经验不足可能导致检索不准。建议引入 LangChain 预置的高级检索策略（如 `ParentDocumentRetriever`）。
- **数据一致性风险**：MySQL 中的知识库元数据状态与 ChromaDB 中的向量数据可能出现不一致（例如向量化失败但 MySQL 状态已更新）。需要在异步任务中增加完善的错误处理和状态回滚机制。
