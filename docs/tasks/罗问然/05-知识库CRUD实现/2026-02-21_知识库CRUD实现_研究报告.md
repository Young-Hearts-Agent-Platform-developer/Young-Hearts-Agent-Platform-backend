## 发现摘要

知识库的 CRUD 核心围绕 `KnowledgeItem`（知识条目）和 `KnowledgeChunk`（知识切片）两个数据模型展开。当前代码库中尚未实现相关的 SQLAlchemy 模型、Pydantic Schemas 和 FastAPI 路由。CRUD 操作主要由 `app/services/knowledge_service.py` 处理，涵盖条目的创建（草稿/待审核）、发布列表查询、详情查询、编辑、审核（专家权限）以及文件上传（触发异步切片任务）。知识库的元数据存储在 MySQL 中，而向量数据存储在 ChromaDB 中，两者通过状态机（如 `published` 状态）保持同步。

## 当前实现分析

目前代码库中 `app/models/` 和 `app/schemas/` 目录下尚未创建 `knowledge.py` 文件。`app/services/knowledge_service.py` 为空文件，`app/api/v1/routes/` 下也尚未创建 `knowledge.py` 路由。知识库的 CRUD 逻辑完全缺失，需要从零开始实现。

根据设计文档，知识库的 CRUD 涉及以下核心接口：
- `GET /api/knowledge/items`: 搜索/列出已发布知识条目 (Any)
- `GET /api/knowledge/items/:id`: 获取详情 (Any)
- `POST /api/knowledge/items`: 提交知识条目 (草稿/待审核) (Volunteer, Expert)
- `PUT /api/knowledge/items/:id`: 编辑条目 (Author, Expert)
- `GET /api/knowledge/audit-list`: 获取待审核列表 (Expert)
- `POST /api/knowledge/items/:id/audit`: 审核条目 (Pass/Reject + Comment) (Expert)
- `POST /api/knowledge/upload`: 上传文件进行自动切片 (Volunteer, Expert)

### 核心流程

**1. 创建/编辑流程 (知识贡献)**
```text
用户 (Volunteer/Expert) 提交知识条目 (POST/PUT)
  -> 路由层 (knowledge.py) 校验权限和请求体
  -> 服务层 (knowledge_service.py) 验证数据并保存到 MySQL (KnowledgeItem)
  -> 状态设为 `pending_review` (待审核) 或 `draft` (草稿)
  -> 返回创建/更新结果
```

**2. 审核流程 (专家协同)**
```text
专家 (Expert) 获取待审核列表 (GET /audit-list)
  -> 专家提交审核结果 (POST /audit, Pass/Reject)
  -> 服务层更新 MySQL 中 KnowledgeItem 的状态
  -> 若 Pass，状态更新为 `published`
  -> 触发异步任务 (knowledge_tasks.py) 将内容切片并向量化存入 ChromaDB
```

**3. 查询流程 (知识查阅)**
```text
普通用户/前端请求已发布列表 (GET /items)
  -> 服务层从 MySQL 查询状态为 `published` 的 KnowledgeItem
  -> 返回列表数据 (支持分页、分类、标签过滤)
```

### 关键代码片段

**建议的 SQLAlchemy 模型 (`app/models/knowledge.py`)**:
```python
from sqlalchemy import Column, Integer, String, Text, JSON, DateTime, ForeignKey
from sqlalchemy.sql import func
from app.models import Base

class KnowledgeItem(Base):
    __tablename__ = "knowledge_items"

    id = Column(Integer, primary_key=True, autoincrement=True)
    title = Column(String(255), nullable=False)
    summary = Column(String(512))
    content = Column(Text, nullable=False)
    tags = Column(JSON, default=list)
    category = Column(String(100))
    author_id = Column(Integer, ForeignKey("users.id"))
    status = Column(String(32), default="draft") # draft, pending_review, published, rejected, archived
    review_comments = Column(Text)
    reviewed_by = Column(Integer, ForeignKey("users.id"))
    reviewed_at = Column(DateTime)
    is_deleted = Column(Boolean, default=False, comment="软删除标记")
    created_at = Column(DateTime, server_default=func.now())
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now())

class KnowledgeChunk(Base):
    __tablename__ = "knowledge_chunks"

    id = Column(Integer, primary_key=True, autoincrement=True)
    item_id = Column(Integer, ForeignKey("knowledge_items.id", ondelete="CASCADE"))
    content_chunk = Column(Text, nullable=False)
    vector_id = Column(String(255))
    sequence = Column(Integer)
```

## 架构洞察

- **双存储架构**：知识库的元数据（标题、摘要、作者、状态等）存储在 MySQL 中，便于进行复杂的业务查询（如按状态过滤、分页、权限控制）。知识库的向量数据存储在 ChromaDB 中，仅用于 RAG 检索。
- **状态机驱动**：知识条目的生命周期由状态机管理（`draft` -> `pending_review` -> `published` / `rejected`）。只有 `published` 状态的数据才会被向量化并用于 RAG，确保了知识库内容的权威性和准确性。
- **解耦设计**：CRUD 业务逻辑（`knowledge_service.py`）与耗时的向量化操作（`knowledge_tasks.py`）解耦，保证了 API 的响应速度。

## 潜在风险和边缘情况

- **并发审核冲突**：多个专家同时审核同一个条目可能导致状态冲突。需要在服务层引入乐观锁（如基于 `updated_at` 字段）或数据库事务来保证一致性。
- **大文本处理超时**：知识条目内容可能非常长，直接在 HTTP 请求中传输和处理可能导致超时或内存溢出。建议限制单次提交的文本长度，或强制使用文件上传（`POST /upload`）并异步处理。
- **数据一致性**：如果 MySQL 中的状态更新为 `published`，但异步向量化任务失败，会导致 MySQL 和 ChromaDB 数据不一致。需要实现重试机制和状态回滚（如向量化失败则将状态改回 `pending_review` 或标记为 `error`）。

## 已确认的设计决策

- **分类与标签管理**：知识条目的标签（`tags`）和分类（`category`）直接作为字符串/JSON 存储在 `KnowledgeItem` 表中，不引入独立的字典表。
- **版本控制**：审核拒绝后，原作者修改后重新提交时，直接覆盖原记录，不进行多版本控制。
- **删除机制**：采用软删除机制，在 `KnowledgeItem` 模型中增加 `is_deleted` 字段。
