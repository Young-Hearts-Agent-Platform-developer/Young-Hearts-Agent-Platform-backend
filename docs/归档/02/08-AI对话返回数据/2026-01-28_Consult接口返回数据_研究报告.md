## 研究问题

目前后端 `POST /api/v1/consult/chat` 接口在进行 AI 对话时，返回的原始数据是什么样的？是否存在格式规范问题？

## 发现摘要

当前接口虽然在 HTTP 响应头中声明 `Content-Type: text/event-stream`，但实际返回的数据流**并非标准的 Server-Sent Events (SSE) 格式**。
它返回的是一个自定义格式的混合文本流：
1. **AI 内容**：直接发送文本片段（Chunks）。
2. **特殊标记**：用于携带元数据或状态，如 `[ERROR]` 和 `[TOPIC]{...}`。

这种实现方式实际上是 HTTP 分块传输（Chunked Transfer Encoding）承载自定义文本协议，而非标准的 SSE。

## 当前实现分析

### 1. 响应头分析
代码中显式设置了 Media Type：
```python
# app/api/v1/routes/consult.py L132
return StreamingResponse(event_stream(), media_type="text/event-stream")
```
这告诉客户端期望 SSE 格式，但 Body 内容未遵循协议。

### 2. 数据流结构
实际数据流由以下三部分组成：

#### A. 正常对话内容
RAG 服务生成的每一个 token 或 chunk 直接被 yield 出来，没有任何前缀或后缀。
```python
# app/api/v1/routes/consult.py L109-L111
async for chunk in async_chat_with_rag(...):
    ai_reply += chunk
    yield chunk
```
**数据示例**：
```text
你好
，
我
是
...
```

#### B. 错误处理
如果发生异常，会发送 `[ERROR]` 标记。
```python
# app/api/v1/routes/consult.py L115
yield f"[ERROR]{error_msg}"
```

#### C. 会话主题 (Topic)
在流结束前，会发送会话主题信息。
```python
# app/api/v1/routes/consult.py L131
yield f"[TOPIC]{json.dumps({'topic': topic})}"
```

### 3. 完整流示例
一个典型的响应流（Raw Body）看起来像这样：
```text
你好
，
很高兴
见到你
。
[TOPIC]{"topic": "打招呼"}
```

## 架构洞察与风险

### 1. 协议合规性问题
标准的 SSE 格式要求每条消息以 `data: ` 开头，并以双换行符 `\n\n` 结尾。
*   **当前实现**：`ChunkContent`
*   **标准 SSE**：`data: ChunkContent\n\n`

**风险**：
*   使用标准 SSE 客户端库（如浏览器的 `EventSource` API）可能无法触发 `onmessage` 事件，或者无法正确解析数据，因为它们期待特定的格式。
*   当前前端实现必须使用通用的 `fetch` API 并手动读取 `ReadableStream` 来解析这种自定义格式。

### 2. 解析歧义风险
使用 `[ERROR]` 和 `[TOPIC]` 作为特殊分隔符存在微小的碰撞风险。
*   **风险**：如果 AI 的回复内容中碰巧包含了字符串 `[TOPIC]`，前端解析器可能会将其误认为是元数据开始，导致内容被截断或解析错误。虽然概率较低，但在健壮性设计中应避免内容与控制信令混用同一通道且无转义机制。

### 3. 建议改进方向
建议迁移到标准的 SSE 格式或 NDJSON (Newline Delimited JSON) 格式。

**方案 A：标准 SSE (推荐)**
```text
event: message
data: 你好

event: message
data: ，

event: topic
data: {"topic": "打招呼"}
```

**方案 B：NDJSON**
```json
{"type": "content", "data": "你好"}
{"type": "content", "data": "，"}
{"type": "topic", "data": "打招呼"}
```
