## 当前实现分析

### 1. API 路由现状
- `/api/consult/chat` 已实现，参数无 session_id，未持久化消息。
- 未见 `/api/consult/sessions` 相关路由（创建、列表、详情）。

【补充】
- `/api/consult/chat` 需增加 `session_id` 参数，AI回复需写入 ConsultationMessage。
- 会话与消息接口需做用户身份校验，普通用户仅能访问自己的数据。

### 2. 数据模型与接口标准
- `ConsultationSession`：id, user_id, topic, created_at, is_archived
- `ConsultationMessage`：id, session_id, role, content, sources, created_at
- 标准接口：
  - POST `/api/consult/sessions` 创建会话
  - GET `/api/consult/sessions` 历史会话列表
  - GET `/api/consult/sessions/:id` 会话消息详情
  - POST `/api/consult/chat` 发送消息并获取AI回复（建议带 session_id）

【补充】
- 所有会话与消息均需与 user_id 关联，接口需校验用户身份。
- 管理员可访问全部数据，普通用户仅能访问自己的。

### 3. 服务层建议
- 新建 service 层：会话创建、查询、消息持久化、AI回复写入。
- 需与用户身份（user_id）关联，支持分页、权限校验。

【补充】
- `/api/consult/chat` 服务需在 AI 回复后，将消息持久化到 ConsultationMessage。
- 权限校验逻辑：普通用户仅能操作/查询自己的 session/message，管理员可全量访问。

### 核心流程

```
用户进入咨询页 →
  1. 创建新会话（POST /api/consult/sessions）
  2. 获取历史会话列表（GET /api/consult/sessions）
  3. 查看会话详情（GET /api/consult/sessions/:id）
  4. 发送消息（POST /api/consult/chat，必须带 session_id）
  5. AI流式回复，消息持久化到 ConsultationMessage
  6. 用户仅能访问自己的会话和消息，管理员可见全部
```

## 架构洞察

- 建议补充 ConsultationSession/Message 的 models、schemas、service 层，API路由与前端标准对齐。
- 流式输出建议带 session_id，AI回复与消息持久化解耦。
- 会话与消息需与 user_id 关联，支持多端同步与权限控制。
- 列表接口需支持分页，详情接口需校验权限。

【补充】
- `/api/consult/chat` 必须带 session_id，AI回复需实时写入 ConsultationMessage。
- 权限控制需区分普通用户与管理员，防止数据越权。

## 潜在风险和边缘情况

- 未持久化消息，历史会话无法回溯。
- session_id 缺失导致多端同步与权限校验困难。
- 流式输出异常需兜底，消息写入失败需重试。
- 用户身份未校验，可能导致数据泄露。

【补充】
- session_id 校验不严或权限判断失误，可能导致用户越权访问他人数据。
- AI回复未及时持久化，可能丢失关键信息。
